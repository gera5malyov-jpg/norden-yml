# Универсальный промт: подключение нового поставщика через GitHub

Подключи нового поставщика к моей системе через GitHub Actions.

- Название поставщика: [ВСТАВИТЬ]
- Куда загружать:

  - Webasyst: [ДА/НЕТ]
- Тип товара Webasyst: [ВСТАВИТЬ ИЛИ ОСТАВИТЬ ПУСТЫМ]
- Префикс артикула: [ВСТАВИТЬ]
- Характеристика-маркер, например Webasyst=334: [ВСТАВИТЬ]
- Категории: [БЕЗ КАТЕГОРИИ / КОПИРОВАТЬ ИЗ ИСТОЧНИКА / ДРУГОЕ]
- Склады назначения: [ВСТАВИТЬ]

## Как работать

1. Всё реализуй через GitHub Actions в существующем репозитории. Не используй отдельные ChatGPT-автоматизации, если я прямо не попросил.

2. Сначала самостоятельно исследуй источник:
   - количество товаров;
   - поле артикула;
   - название;
   - описание;
   - цена;
   - старая цена;
   - закупочная цена, если есть;
   - остаток;
   - категории;
   - бренд;
   - изображения;
   - все характеристики;
   - габариты/вес/упаковки;
   - URL товара;
   - доступность товара.

3. Перед тем как задавать мне вопросы, проверь:
   - существующие скрипты и workflows в GitHub;
   - доступные secrets;
   - существующие типы товаров Webasyst;
   - существующие склады Webasyst;
   - склады Яндекс КИТ;
   - существующие характеристики;
   - уже загруженные товары этого поставщика;
   - возможные дубли.

4. Не задавай вопросы о том, что можно определить автоматически. Спроси меня только о реально неоднозначных правилах.

5. Если чего-то не хватает, задай одним сообщением все необходимые вопросы. Обязательно уточни, если не указано однозначно:
   - какой источник является основным и есть ли fallback;
   - какой артикул считать основным;
   - какой префикс добавлять;
   - какое поле использовать как уникальный ключ;
   - что записывать в "Код для сайта";
   - какой бренд ставить;
   - тип товара Webasyst;
   - нужна ли категория;
   - какие склады использовать;
   - откуда брать остаток;
   - что делать при отсутствии товара в источнике: оставить / поставить 0 / архивировать;
   - как считать цену, старую цену, закупочную и минимальную;
   - нужно ли обновлять существующие описания/характеристики или только пустые;
   - какие характеристики исключить;
   - как работать с изображениями;
   - как формировать URL;
   - как часто обновлять;
   - куда отправлять отчёт.

## Защита от дублей

6. До создания товара обязательно выполни полную сверку существующих карточек поставщика в целевой системе.

7. Для сопоставления по умолчанию проверяй все настроенные идентификаторы:
   - SKU;
   - Артикул;
   - Код / код поставщика;
   - Внешний ID / внешние ID поставщика;
   - Код для сайта.
   Поля могут храниться как системные поля или характеристики KIT — проверять оба варианта, если они доступны.

8. Один источник-артикул должен соответствовать одной активной карточке. Если совпал хотя бы один надёжный уникальный идентификатор, новую карточку не создавать до разрешения конфликта.

9. Никогда не используй поиск только по префиксу SKU и не ограничивай сверку последними страницами каталога. Перед массовым созданием новых товаров делай полную live-сверку всех активных карточек данного поставщика.

10. Название товара НЕ является универсальным идентификатором. Для каждого нового поставщика отдельно спроси пользователя, разрешено ли учитывать название при сопоставлении дублей. До получения ответа политика по названию = СПРОСИТЬ, то есть автоматическое сопоставление по названию запрещено. Правило одного поставщика нельзя переносить на другого.

11. Для каждого поставщика зафиксируй политику сопоставления в `config/supplier_identity_policy.json`: какие идентификаторы использовать и разрешено ли сопоставление по названию.

12. Если дубли уже есть:
   - сначала покажи/зафиксируй их количество;
   - выбери основную карточку по понятному правилу: исходная/самая старая/самая полная;
   - лишние перенеси в архив или скрыть, если архивирование через API недоступно; остатки дубля обязательно поставить 0;
   - исключи дубль из рабочего mapping, чтобы он больше не получал цену/остаток;
   - после очистки проверь, что на один уникальный идентификатор остаётся одна рабочая карточка.

## Первоначальная загрузка

10. Перед массовой загрузкой сделай live smoke-test на одном товаре.

11. После smoke-test обязательно прочитай созданную карточку обратно из целевой системы и проверь:
   - тип товара;
   - артикул;
   - Код для сайта;
   - цену;
   - старую цену;
   - остаток и нужный склад;
   - описание;
   - краткое описание;
   - изображения;
   - характеристики;
   - URL;
   - категорию или её отсутствие.

12. Если smoke-test успешен, загружай весь каталог без дополнительных вопросов.

13. Для нового товара переноси все разрешённые данные источника:
   - название;
   - описание;
   - цены;
   - остатки;
   - характеристики;
   - изображения;
   - бренд;
   - вес/габариты/упаковки;
   - другие полезные поля.

14. Если я указал исключённые характеристики, никогда не создавай и не заполняй их.

## Изображения

15. Если изображения нужно хранить в Webasyst через внешние ссылки, формируй краткое описание так:

[extimg]
URL_1
URL_2
URL_3
[/extimg]

Не загружай эти изображения в стандартную галерею, если я отдельно не попросил.

## URL Webasyst

16. После создания карточки генерируй нормальный читаемый URL:
   - транслитерация названия;
   - дефисы вместо пробелов/символов;
   - в конце уникальный артикул;
   - не оставляй URL в виде внутреннего цифрового ID.

Пример:
stol-kenner-1000-m-venge-steklo-beloe-glyanets-334-326506

## Ежедневная синхронизация

17. После первоначальной загрузки настрой GitHub Actions по указанному расписанию.

18. Для существующих товаров по умолчанию ежедневно обновляй только:
   - цену;
   - старую цену;
   - остаток.

Не переписывай название, описание, URL и характеристики без необходимости, если я не задал другое правило.

19. Если в источнике появляется новый товар:
   - автоматически создай его полностью по тем же правилам;
   - не жди ручного запуска;
   - не создавай дубль.

20. Если цена/остаток не изменились, не делай лишнюю запись в API.

## Отчётность

21. После первого полного импорта проверь итог:
   - товаров в источнике;
   - обработано;
   - создано;
   - обновлено;
   - без изменений;
   - дубли;
   - ошибки;
   - изображения;
   - характеристики.

22. Не говори "готово", пока не проверишь реальную карточку в целевой системе.

23. Если указан email, после полного успешного импорта отправь письмо через GitHub Actions. Письмо должно отправляться только после подтверждённого успешного результата без ошибок.

24. В конце напиши мне коротко:
   - сколько товаров загружено;
   - сколько обновлено;
   - сколько ошибок;
   - какое расписание настроено;
   - какие правила применены;
   - идентификатор последнего GitHub run.

## Дополнительное правило

Если мои новые инструкции противоречат старым, используй самые новые инструкции именно для этого поставщика и не переносись автоматически правила другого поставщика.
